# Pick Dory's loop count per request

**Use llama.cpp for the first phases, decide loops per request rather than per token, and make the controller a measured choice between a text baseline and a hidden-state probe.** Dory's training assigned loop counts per prompt or per rollout worker, never per token ([arXiv 2611.03998](https://arxiv.org/html/2611.03998v1)), so per-token switching is out of distribution and only worth attempting after per-request control works. The strongest per-request evidence, from [Predictive Scheduling (arXiv 2602.01237)](https://arxiv.org/abs/2602.01237), favors predictors on mid-layer hidden states over raw-text classifiers. The [Continuous Depth Batching](https://arxiv.org/html/2608.09444v1) result that rejects prompt-only gates measures per-token exits, so it does not settle the per-request question. An online probe reads Dory's own states from one k=1 prefill, which costs roughly **2-3 s per 1k prompt tokens** on this M4 (my estimate). It therefore has to beat a cheap text baseline at matched end-to-end latency to earn its place. On a 1k-token prompt with a 300-token answer, I estimate **about 11 s at k=1, 17 s at k=2, and 27 s at k=4**, with weights around 3.7 GB resident. Coding and agentic prompts must never go to k=1, because the paper's largest single gain is on SWE-bench Verified between 1 and 2 loops.

## Runtime: llama.cpp for control, MLX only when per-token pays off

The notes disagree on runtime. One calls MLX "the only realistic path for per-request loop control" because a loop argument on a Python forward pass is trivial ([m4 notes](https://arxiv.org/html/2611.03998v1)). The other, the task premise, treats llama.cpp as load-time only. Both are right about the stock builds: the GGUF key `dory.num_loops` is set at load through `--override-kv`, and the [BF16 model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16) documents the same knob for vLLM. The reconciling point is that per-request control does not need per-token control. If `num_loops` is read into model hyperparameters, moving it to a per-context parameter, or running one context per k over a single loaded model, is a small C++ patch to the Dory PR ([ggml-org/llama.cpp#30306](https://github.com/ggml-org/llama.cpp/pull/30306)). I have not read that PR, so this is an inference to verify in Phase 0. Shared weights keep memory near one Q5_K_M copy, about **3.7 GB** ([modelfit.io](https://modelfit.io/blog/nvidia-nemotron-labs-dory-1-0-4b-mac-memory-requirements/)). Quality is also better documented on this path: the paper's Table 4 shows Q5_K_M-QAD tracking BF16 at four loops (GPQA 72.66 against 72.16 for BF16), while no Dory-specific quality number exists for MLX 4-bit.

The MLX route is real but expensive. ArcadaLabs ported Ouro by dropping a custom `ouro.py` into `mlx_lm/models` ([ArcadaLabs](https://huggingface.co/ArcadaLabs/Ouro-2.6B-mlx-bf16)), and their single informal prompt puts MLX at about **1.7x** the speed of PyTorch MPS, measured on an M5 Pro rather than an M4. That number does not transfer to a Q5_K_M llama.cpp versus 4-bit MLX comparison, which nobody has run for Dory. The MLX port also needs a parity reference, and the only one is the contributor fork that the notes could not identify by name.

The architecture itself is in conflict. The BF16 card and secondary coverage describe 8 input, 20 recurrent, and 8 output blocks, while the arXiv summary reports 16, 40, and 16 layers ([model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16); [arXiv](https://arxiv.org/html/2611.03998v1)). The likeliest reconciliation is that the paper counts attention and MLP sublayers separately, which is 2 x 8 and 2 x 20, but this is unverified. The `config.json` settles it in minutes and sets every memory and throughput figure below. Given the Phase 0 outcome, MLX is the fallback for when the llama.cpp patch is infeasible or per-token control is shown to help.

Two memory points follow. At the expected footprint, roughly 8 GB total, the notes' suggested GPU wired-limit raise to 18 GB is unnecessary, and one 24 GB user reported that raising it made crashes worse ([kartit.net](https://www.kartit.net/blog/qwen38-27b-24gb-macbook)). Leave `iogpu.wired_limit_mb` at its default. For the KV cache, per-request control keeps one k for the whole request, so the default `per_loop` mode is the simplest choice. Switch to `last_loop` only if measured KV memory dominates. The paper reports `last_loop` costs about 2 points on Terminal-Bench (22.19 against 20.22) at four loops ([arXiv](https://arxiv.org/html/2611.03998v1)).

## Per-request control matches the training regime; per-token does not

Dory was trained with loop counts assigned at the level of the sample, the prompt, or the rollout worker. Pretraining drew from {1,2,3,4} per optimizer step and microbatch, SFT drew uniformly per sample with a 0.1 one-loop override, and RLVR fixed k per rollout worker with a 4:1:1:1 prompt quota ([arXiv](https://arxiv.org/html/2611.03998v1)). The difficulty curriculum routed harder prompts to deeper loops using a score of 0.3 times pass-rate quantile plus 0.7 times uniform noise. Nothing in training varies loops per token. The paper also has no learned exit gate, so the controller must supply k entirely, and the phrase "elastic depth" means choosing k at inference rather than halting adaptively.

This matters for the design. A per-request controller learns the same mapping the curriculum used, from difficulty to k, with one k governing the prompt and the whole answer. Per-token switching would need an unmeasured mechanism, and Ouro's trained gate and Huginn's KL rule, the two published per-token exits, improve over fixed depth by only 1-3 points at matched depth ([arXiv 2510.25741](https://arxiv.org/html/2510.25741v2)). The paper's claim of **1.3-2.5x fewer output tokens at four loops** conflicts with its own Table 6, which shows roughly a 1.00-1.03x ratio on the listed tasks. I would not budget on token savings at all. NVIDIA advises end-to-end measurement, and the phased plan does that.

Accuracy versus loops is also task-dependent, so the controller should not learn a single cutoff. Knowledge benchmarks flatten after two loops: GPQA Diamond goes 69.19, 72.41, 72.16 across one, two, and four loops, and MMLU-Pro is nearly flat from two up. Agentic and coding tasks keep gaining, with SWE-bench Verified at **50.3, 59.5, and 61.8** and Terminal-Bench at 12.5, 18.1, and 22.2 ([arXiv](https://arxiv.org/html/2611.03998v1)). Every number here is NVIDIA-reported and has no independent reproduction, so the Phase 3 evaluation has to confirm these shapes on the local quantized model.

## Prompt-only gates versus online probes: the evidence splits by target

The Continuous Depth Batching paper is the main obstacle. It reports that a distilled pre-loop gate, which predicts exit before the loop starts, "does not perform well," while a distilled lookahead gate matches its teacher ([arXiv 2608.09444](https://arxiv.org/html/2608.09444v1)). That gate predicts per-step exits inside a batched scheduler, so the result is evidence against prompt-only per-token exits. It does not test a prompt-only per-request budget, which is the question here. The per-request evidence points the other way. Predictive Scheduling trains predictors on the hidden states of middle layers, layers 12-17 being most informative, to allocate a fixed token budget per query, and reports up to **7.9 points** of GSM8K gain over uniform allocation at equal cost. It also finds a LoRA text classifier viable ([arXiv 2602.01237](https://arxiv.org/abs/2602.01237)). That paper studies a different reasoning model, and its checkpoints were not verified.

Laya does not change the picture. It is a 421M ModernBERT-large encoder with a 2-layer decision head, and its base checkpoint is close to chance on typed decisions, at 0.362 for English against 0.766 after fine-tuning ([Laya card](https://huggingface.co/convaiinnovations/laya)). It is a fine-tuning shell with no evidence behind it for loop budgets, and its English checkpoint truncates at 512 tokens. NVIDIA's `prompt-task-and-complexity-classifier` is the better text feature source: a 0.2B DeBERTa that scores six complexity dimensions, trained on 4,024 English prompts, with a GPU-only card that needs an ONNX or MPS path on the Mac ([NVIDIA card](https://huggingface.co/nvidia/prompt-task-and-complexity-classifier)). A logistic regression over its six scores plus prompt length is a cheap baseline that any Laya fine-tune must beat. Laya is worth fine-tuning only if it wins that comparison.

The online probe has a real cost on this machine. Huginn's KL rule and Ouro's gate need several loops before they decide, but a probe does not need to decode anything. One k=1 prefill produces hidden states for every prompt token. My estimate is about 36 effective layers and roughly 8 TFLOP per 1k tokens, which at an assumed 3 TFLOPS achieved is about **2.7 s**. A 300-token answer at k=2 takes about 12 s of decode, so the probe adds roughly 20 percent to a k=2 request. That overhead is about the size of the k=1-versus-k=2 margin, so the probe has to clear it. Truncating the probe to the first 256 prompt tokens is a cheap way to cut the cost, and it is worth measuring.

My verdict: the online probe on a k=1 prefill is the better bet for per-request control, because the only per-request evidence favors hidden states and the probe reads the same activations Dory already computes. Its advantage is unproven on Dory, though, and its prefill cost is a fixed tax on every request. So the text baseline ships first. The probe is promoted only if it beats the baseline at matched end-to-end latency, including its own overhead. If the text baseline matches the probe, prefer the text baseline, which has no overhead.

## Reconciling the notes

The notes conflict on several points that change the plan. Each is resolved below, with the basis for the resolution.

| Conflict | Resolution |
|---|---|
| MLX is the only realistic per-request path, versus llama.cpp is load-time only | Both are load-time in stock form. A per-context `num_loops` patch makes llama.cpp per-request. This is unverified until Phase 0, so MLX is the fallback. |
| Recurrent layers 8/20/8 versus 16/40/16 | Likely sublayer counting, but unverified. Resolve from `config.json` in Phase 0, before any memory estimate is trusted. |
| "Up to eight loops" versus "1-4 loops" | Trained range is 1-4. Six and eight are extrapolation tested in the base-model evals only ([arXiv](https://arxiv.org/html/2611.03998v1)). |
| "1.3-2.5x fewer output tokens" versus Table 6's ~1.0x | Metrics differ and the claim is aggregator-only. Do not budget on token savings. |
| Dory release date 16 Oct versus paper v1 on 2 Nov | Not decision-relevant. Use the weights' commit hash as the reference. |
| llama.cpp PR #30306 and vLLM PR #60149 status | Unverified as of 2026-11-11. Pin a specific fork revision for every run. |
| Prompt-only gates fail (CDB) versus hidden-state probes win (Predictive Scheduling) | Different targets: per-step exits versus per-query budgets. The per-request evidence favors hidden states, and the text baseline is still the cheap first build. |
| Ouro gate beats threshold by 2-3 points versus "trained gates are the way to go" | The gain is small at matched depth and is per-token. Irrelevant to the per-request design except as a reminder to measure. |

## A phased plan with measured gates

The plan runs five phases, each with a go or no-go gate, so no later phase starts on an unmeasured assumption. Times are my estimates.

| Phase | Work | Gate to proceed | Time (est.) |
|---|---|---|---|
| 0. Reference | Fetch `config.json` and the fork. Build llama.cpp at a pinned revision with Metal. Confirm `dory.num_loops` changes output. Measure tok/s and RSS at k=1-4 on Q5_K_M. Settle the 8/20/8 question. | Outputs differ across k, and fixed-k accuracy on 200 GSM8K and MMLU-Pro items shows the expected trend. | 1-2 days |
| 1. Labels | 1,500 prompts drawn from GSM8K train, MMLU-Pro dev, and a coding set such as MBPP or HumanEval. Run each at k=1, 2, 3, 4. Label = smallest k that is correct (or, without gold, agrees with the k=4 answer), ties to the smaller k. Keep a KL stability curve as a soft label. | No class above 80 percent of labels. | Roughly 17 h serial at ~42 s per prompt, 5-9 h with parallel slots |
| 2. Text baseline | NVIDIA classifier scores plus prompt length, logistic regression over k, cross-validated. Laya fine-tune only as a comparator. | Beats fixed k=2 at matched mean k on a held-out split, with a confidence interval. | 1-2 days |
| 3. Hidden-state probe | Mid-layer hidden state at the last prompt token from a k=1 prefill. Needs an eval-callback hook in llama.cpp. Train on the Phase 1 labels. | Beats Phase 2 at matched end-to-end latency, including the probe's prefill cost. | 3-5 days |
| 4. Per-request switching | Implement the per-context `num_loops` patch, or one context per k over shared weights. Measure switch cost. Port to MLX only if the patch is infeasible, or per-token control shows a measured gain. | Switch overhead under 50 ms, and mixed-k requests produce no quality regression. | 1 week, longer if MLX |

The evaluation runs on held-out prompts. Baselines are fixed k=1, 2, and 4, a random policy at matched mean k, and the label-oracle upper bound. Report accuracy against mean k and against end-to-end latency, plus tok/s and peak RSS. With about 300 held-out items, differences under about 3 points are not significant, so use paired bootstrap intervals.

The latency and memory expectations, all estimates to be replaced by Phase 0 measurements, are below.

| Setting | Prefill (1k tokens) | Decode (300 tokens) | Total | Notes |
|---|---|---|---|---|
| k=1 | ~2.7 s | ~8.6 s at 35 tok/s | ~11 s | Easy prompts only. Never for code or agentic. |
| k=2 | ~4.2 s | ~12.5 s at 24 tok/s | ~17 s | Default knee for knowledge tasks. |
| k=4 | ~7.2 s | ~20 s at 15 tok/s | ~27 s | Agentic and coding. |
| Probe overhead | +2.7 s (k=1 prefill) | none | +2.7 s | Truncating to 256 tokens cuts this. |

Memory budget at these sizes: Q5_K_M weights about 3.7 GB, the NVIDIA classifier at 0.2B in fp16 about 0.4 GB, Laya at 421M in fp16 about 0.9 GB if used, and a probe that is negligible. The KV cache for per-loop caching grows linearly with k and cannot be estimated until the config is read. The total stays under about 8 GB, well inside 24 GB, so the controller and the 4B model fit together without memory tuning.

## Conclusion

The decision model matters less than the labels and the cost of the probe. The controller saves time only when easy prompts are common and the accuracy cost of k=1 is small, and the paper's own numbers say k=2 is already the knee for knowledge tasks while k=4 is the lever for agentic work. So the realistic win is routing hard coding and agentic prompts to k=4, keeping knowledge prompts at k=2, and sending only clearly easy prompts to k=1. That is a per-request decision, and Dory's training already supports it.

The open research question is per-token control. Nothing in training or the published evidence shows that per-token variation helps Dory, and the one published mechanism for it, Ouro's gate, gains only a few points at matched depth. The sensible order is to get per-request control working on llama.cpp, measure whether the probe clears its own prefill tax, and treat the MLX port as the only route to per-token control, to be justified by data rather than by the architecture.
